## 一、开场白（口头讲稿，约 3 分钟）

老师好，这次汇报主要有 **三个新进展**：

1. **完成了 benchmark 现状调研**，意外发现两个 2025 年底刚发布的权威数据集几乎直接对口我们的场景 —— **MTBBench**（2025-11, arXiv, ETH+EPFL+HUG）和 **PrimeKGQA**（2024-10, Zenodo，基于 PrimeKG）。这让我们可以从"自造 20 题"升级为"标准 benchmark + 自制补充集"，论文可信度大幅提升。

2. **重新梳理了技术概念的表达方式**。之前的汇报文档偏"什么"（概念罗列），这次补齐了"为什么这么设计"和"具体是什么样"（每个技术点都配一个真实例子）。这是为了回应老师之前"故事讲不好"的反馈 —— 不只是换场景，还要把**技术细节讲得像工程师能读懂、医生也能看懂**。

3. **38 题历史结果的新定位** —— 不是"成绩不好"，而是"角色错位"。它本来就不该做主实验，而应做**组件消融**（证明 Bridge、多角色、KB 各自贡献）。这个定位调整后，历史结果（Bridge Hit = 100%、Pathway F1 = 0.316）就从"看起来勉强"变成"消融章节的黄金证据"。

整体思路还是一句话：**不追求"数据量大"，而追求"故事对 + 证据扎实"**。

## 三、MTB 场景定位（含技术例子）

### 3.1 一句话定义

> **GDgpt 帮助肿瘤科医生在 MTB 准备阶段，快速生成某患者的"基因—疾病—通路—药物"机制解释报告，所有结论可追溯到知识图谱的具体边，并明确区分"图谱事实"与"LLM 推测"。**

### 3.2 什么是 MTB？（给一个场景故事）

**场景示例（基于 2024 年真实病例改编）：**

> 张医生是某三甲医院肿瘤科住院医。下周三下午是 MTB 例会，他负责汇报 3 位复杂患者。其中一位是 **58 岁女性 HER2+ 乳腺癌患者**，一线曲妥珠单抗（Trastuzumab）治疗 14 个月后出现**肝转移**，基因检测报告显示 **PIK3CA H1047R 突变**。
>
> 张医生要在周二晚上准备：
> 1. HER2+ 乳腺癌 trastuzumab 耐药后还有哪些可选靶向药？（答：T-DXd、Tucatinib、Margetuximab）
> 2. PIK3CA 突变在这个场景下影响治疗决策吗？（答：联合 mTOR 抑制剂 / alpelisib 证据）
> 3. 这些药物的机制通路是什么？（答：PI3K/AKT/mTOR + HER2-ERBB 信号通路）
>
> 传统流程：OncoKB 查 HER2 + 查 PIK3CA + CIViC 查耐药机制 + PubMed 读 2-3 篇文献 + NCCN 指南查二线方案 ≈ **1.5 小时/例**。
>
> **GDgpt 的价值**：把这 1.5 小时缩短到 **10 分钟生成结构化报告 + 15 分钟医生审核**，并且每一条结论后面都挂着"这是 PrimeKG 里 (Trastuzumab) -[TARGETS]-> (ERBB2) 这条边支持的"，不像 GPT-4o 那样给出一句话就让你猜它是从哪学来的。

### 3.3 为什么 MTB 适合我们

| 维度 | 匹配情况 | 具体证据 |
|---|---|---|
| **KG 数据契合** | ⭐⭐⭐⭐⭐ | 20 种疾病里 18 种是癌症（breast/lung/hepatocellular/ovarian/prostate/pancreatic/colorectal 等） |
| **KG 数据密度** | ⭐⭐⭐⭐ | ASSOCIATED_WITH 30,854 条；TARGETS 18,392 条；TREATS+OFF_LABEL 574 条 |
| **Bridge 多跳契合** | ⭐⭐⭐⭐⭐ | MTB 医生天然思考 `疾病→基因→通路→药物` 链 |
| **学术热点** | ⭐⭐⭐⭐ | Knowledge Connector（Nature Commun 2026）、DeepRare（Nature 2026）、RareAgents（AAAI-26 Oral）都聚焦"KG+Agent+临床决策"三元组 |

### 3.4 7 角色 → MTB 席位映射（附每个角色的实际发言例子）

为了让老师直观理解，下面给出**同一个病例**在 7 个角色眼里是什么样的：

**病例输入**：*58yo F, HER2+ breast carcinoma, liver met, post-trastuzumab progression, PIK3CA H1047R.*

| Agent | 对应 MTB 席位 | 该角色的典型发言（示例） |
|---|---|---|
| **GeneCurator**（基因管理员） | 分子病理学家 | "ERBB2 在本病例高表达且为驱动基因；PIK3CA H1047R 属于 hotspot gain-of-function，位于 kinase domain。" |
| **DiseaseMechanismAnalyst**（疾病机制） | 临床肿瘤学家 | "HER2+ 转移性乳癌的 trastuzumab 耐药常见机制：HER2 下游旁路（PI3K/AKT 过度激活）或 HER2 受体剪接。此例 PIK3CA 突变提示前者。" |
| **PathwayBiologist**（通路生物学） | 转化医学研究员 | "涉及通路：ERBB → PI3K/AKT/mTOR → mTORC1 → 蛋白合成。两条通路在此病例同时激活（HER2 表达 + PIK3CA 突变）。" |
| **PhenotypeMapper**（表型映射） | 临床遗传师 | "相关 HPO：肝转移（HP:0002315）、乳腺癌家族史查询中。" |
| **DrugMechanismAnalyst**（药物机制） | 临床药师 | "T-DXd（DS-8201）= HER2 ADC，可绕过耐药；Alpelisib 是 PI3Kα 选择性抑制剂，对 PIK3CA H1047R 有效；Tucatinib 针对 HER2-TKI。" |
| **EvidenceReviewer**（证据评审） | 方法学质控 | "DESTINY-Breast03 (T-DXd, NEJM 2022) 证据等级 I；SOLAR-1 (Alpelisib, NEJM 2019) 证据等级 I；OncoKB Level 1。" |
| **HypothesisIntegrator**（假设整合） | **MTB 主席** | "综合建议：首选 T-DXd 作为二线；若加 Alpelisib 需关注高血糖和皮疹副作用；PI3K/AKT 联合阻断需谨慎。所有推荐均附 KG 边。" |

**✨ 对标价值**：这 7 角色设计直接对标 **RareAgents（AAAI-26 Oral，清华）** 的多 Agent MDT 架构，但我们把角色**具体锚定到肿瘤学 MTB 席位**，而非泛泛的"医生团队"。这是论文里 Method 章节一张核心表。

## 四、技术概念详解（含 6 个实例）

> 这一章是回应老师"技术要讲清楚"的反馈，**每个核心概念都配一个可以直接写进论文的例子**。

### 4.1 知识图谱（PrimeKG / Task KG）

**什么是 PrimeKG？**
> 2023 年 Harvard / Marinka Zitnik 组发布的**全景生物医学知识图谱**，整合 20 个权威数据源（DisGeNET、DrugBank、Reactome、HPO、ClinVar 等），覆盖 disease / gene / drug / pathway / phenotype / anatomy / side-effect 等 10+ 种节点。

**我们用的是 PrimeKG 的子图（Task KG）**：

```
Task KG 统计：
  节点 10,133 | 边 87,838 | 20 种疾病（18 癌症 + 2 非癌）
  -------------------------------------------
  节点分布：Drug 4730 | Gene 3582 | Pathway 1725 | Phenotype 76 | Disease 20
  关键边：ASSOCIATED_WITH(Disease-Gene) 30,854
        TARGETS(Drug-Gene) 18,392
        INVOLVED_IN(Gene-Pathway) ~2.5w
        TREATS + OFF_LABEL + CONTRAINDICATED 574
```

**例 4.1.1 | KG 里的一条真实"边"长什么样**：

```cypher
(Trastuzumab:Drug {id:"DB00072", mech:"HER2 monoclonal antibody"})
   -[:TARGETS {source:"DrugBank", evidence:"approved"}]->
(ERBB2:Gene {id:"ENSG00000141736", symbol:"ERBB2", alias:"HER2"})
```

这条边对医生意味着：**Trastuzumab 这个药靶点是 ERBB2 基因，来源是 DrugBank 且已获批**。论文里可直接说：*"Our system cites edge `(Trastuzumab)-[TARGETS]->(ERBB2)` from DrugBank."* 这就是"可追溯"的原子单位。

### 4.2 单跳查询 vs Bridge 多跳查询

**单跳查询**（1 次图遍历）：

| Intent | 做什么 | Cypher 样子（简化） |
|---|---|---|
| DiseaseToGene | 查一种疾病的关联基因 | `MATCH (d:Disease {name:$x})-[:ASSOCIATED_WITH]->(g:Gene) RETURN g LIMIT 8` |
| GeneToDisease | 查一个基因涉及哪些疾病 | `MATCH (g:Gene {name:$x})<-[:ASSOCIATED_WITH]-(d:Disease) RETURN d` |
| DrugToGene | 查一个药靶点是哪些基因 | `MATCH (dr:Drug)-[:TARGETS]->(g:Gene {name:$x}) RETURN dr` |
| ... | 共 8 种单跳意图 | ... |

**Bridge 多跳查询**（2-3 次遍历串成"链"）：

| Intent | 做什么 | 链式模式 |
|---|---|---|
| **DiseaseGenePathwayBridge** | "疾病→基因→通路"三跳链 | `Disease → Gene → Pathway` |
| **DrugTargetDiseaseBridge** | "药→靶点→疾病"三跳 | `Drug → Gene → Disease` |
| **GenePathwayDrugBridge** | "基因→通路→药"三跳 | `Gene → Pathway → Drug(via Target)` |

**例 4.2.1 | Bridge 查询在病例上的真实运行**

输入：`"breast carcinoma 的治疗机制"`

- **单跳查询**只能得到孤立片段：
  - Disease→Gene: `[ERBB2, BRCA1, PIK3CA, TP53, ...]`
  - Gene→Pathway: `[ERBB2 → ERBB signaling]`（需要另一次查）
  - 医生要自己在脑子里把这些拼起来。

- **Bridge 查询**一次返回**链**：
  ```
  breast carcinoma
      ├── ERBB2 ── ERBB signaling pathway
      ├── PIK3CA ── PI3K/AKT/mTOR signaling
      └── BRCA1 ── DNA damage repair
  ```
  医生看到的就是一张"解释图"，可以直接讲给 MTB 其他成员听。

**Bridge 是我们的"论文卖点"之一**：GPT-4o 也能说出 HER2 和 ERBB signaling 有关，但**不能明确说"这个判断来自 KG 里哪条边"**。Bridge 的每一跳都是 KG 边，全部可追溯。

### 4.3 多角色协同：同轮互盲 + 跨轮可见（Blind-then-Share）

**问题**：多个 LLM Agent 如果一开始就看到彼此答案，容易**趋同**（"第二个 Agent 懒得独立思考，附和第一个"）。这是多 Agent 系统的经典坑。

**我们的解法**：参考 MDTeamGPT（原始论文）设计 **Blind-then-Share**：

```
Round 1（互盲）：
  7 个 Agent 各自独立回答，看不到彼此。
  → 保证视角多样性（基因视角 / 通路视角 / 药物视角不会被带偏）

Round 2（可见）：
  Round 1 的全部答案广播给 7 个 Agent
  → Agent 可以"反思 + 争辩 + 修正"

...

Round 6（收敛）：HypothesisIntegrator 综合所有意见出最终报告
```

**例 4.3.1 | 互盲机制的真实价值**

在 eval-001（breast carcinoma 案例）中：
- Round 1 互盲时：GeneCurator 提到 `BRCA1/2`，DrugMechanismAnalyst 提到 `PARP 抑制剂（Olaparib）`，**但两者独立给出，没互相看到**。
- Round 2 看到彼此后：HypothesisIntegrator 把两个视角串起来 → "BRCA1/2 → DNA 损伤修复缺陷 → PARP 抑制剂协同致死"。
- 如果没有互盲，Round 1 就可能因为先说出"PARP"而把所有 Agent 都拉过去，**错过其他重要通路**。

配置参数（写进论文 Method 表）：
```
max_rounds = 6
temperature(生成型 Agent) = 0.7   ← 鼓励多样
temperature(评审型 Agent) = 0.0   ← 确定性判定
```

### 4.4 KG Prefetch：先查图，再让 Agent 说话

**问题**：如果让 7 个 Agent 各自去查 KG，会触发 7 × 多次 Neo4j 查询，**又慢又有不一致风险**（同一个问题查 7 次可能返回不同条目）。

**解法**：在 Agent 启动前，**先用 Triage Agent 识别查询意图 → 一次性拉齐所有需要的 KG 数据 → 作为"事实注入"喂给所有 Agent**。

**例 4.4.1 | Prefetch 的完整流程**

```
用户问："breast carcinoma 的治疗机制"
    ↓
[Step 1] Triage Agent：识别意图 = {DiseaseToGene, DiseaseToPathway, DiseaseToDrug, DiseaseGenePathwayBridge}
    ↓
[Step 2] KG Prefetch：并行触发 4 次 Neo4j 查询，合并为 fact_sheet：
    {
      "genes": ["ERBB2", "BRCA1", "PIK3CA", "TP53", ...],
      "pathways": ["ERBB signaling", "PI3K/AKT", "DNA repair", ...],
      "drugs": ["Trastuzumab", "Olaparib", "Tamoxifen", ...],
      "bridges": [{"chain": "breast carcinoma → ERBB2 → ERBB signaling"}, ...]
    }
    ↓
[Step 3] Consultation：fact_sheet 注入到每个 Agent 的 prompt，7 个 Agent 基于同一份 KG 事实发言
    ↓
[Step 4] Safety Review：EvidenceReviewer 检查每条结论是否挂到 fact_sheet 的某条边
```

这样做的好处：
- **一致性**：7 个 Agent 看到的 KG 事实完全一致，避免"A Agent 说有 BRCA1，B Agent 说没有"的尴尬
- **可追溯**：Safety Review 时只要对 fact_sheet 里的边做索引即可
- **速度**：Neo4j 查询从 7×N 降到 1×N

### 4.5 双知识库：CorrectKB + ChainKB

**这是我们参考 MDTeamGPT 的反思学习机制**。

| 知识库 | 存什么 | 怎么用 |
|---|---|---|
| **CorrectKB**（正确经验库） | 过去问答中**正确且获批**的推理链（FAISS 向量） | 新问题来时，先 top-k 检索相似成功案例作为"few-shot" |
| **ChainKB**（错误反思库） | 过去**被 Safety Review 驳回**的推理链 + 驳回理由 | 新问题来时，检索相似失败案例，作为"避坑提醒" |

**例 4.5.1 | ChainKB 的真实反思条目**

```json
{
  "case_id": "eval-017",
  "failed_chain": "KRAS 突变 → 上调 MAPK → Cetuximab 有效",
  "why_rejected": "Cetuximab 对 KRAS 突变型结直肠癌无效（NEJM 2008），反而是抗性标志。违反指南。",
  "lesson_embedded": "若 KRAS 突变且结直肠癌，排除 Cetuximab/Panitumumab（抗 EGFR ADT）"
}
```

下次 Agent 再处理 KRAS + 结直肠癌病例时，ChainKB 会召回这条失败案例，**阻止 Agent 重犯错误**。

### 4.6 FAISS 向量检索（给没接触过向量库的老师解释）

**FAISS 是 Facebook 开源的向量相似度搜索库**。

工作原理一句话：**把每个"问题-答案对"用 LLM 嵌入成 1536 维向量 → 存到索引 → 新问题来时用欧氏距离/余弦找最相似的 top-k**。

**例 4.6.1**：
- 新问题："HER2 阳性乳腺癌有哪些靶向药？"
- FAISS 在 CorrectKB 召回最相似的历史案例：
  - case-5: "ERBB2 amplification breast cancer treatment options"（相似度 0.89）
  - case-12: "Trastuzumab resistance mechanisms"（相似度 0.82）
- 这两个 case 的正确答案作为 few-shot 放进新问题的 prompt → 帮助 Agent 少走弯路。

## 五、Benchmark 调研重大发现 ✨

> **这一章是本次汇报最重要的新内容**。上次汇报后我系统调研了"是否有现成的 benchmark 可以用"，结果**发现 2 个 2024-2025 新出的数据集几乎完美对口**。

### 5.1 为什么要做这个调研

老师上次反馈 "测试集要面向场景"。我的第一反应是自己造 20 题 MTB 场景集。**但做之前我先问自己一句：有没有已有的权威 benchmark？**

研究效率第一铁律：**有现成的就别自己造**。理由：
- 自造数据集容易被 reviewer 质疑"有偏"
- 需要医生验证，但医生资源稀缺
- 没有 SOTA 可对标

### 5.2 发现 1：MTBBench（2025-11，arXiv）⭐⭐⭐⭐⭐

**论文**：arxiv.org/abs/2511.20490（2025-11，ETH Zürich + EPFL + HUG）
**GitHub**：github.com/bunnelab/MTBBench
**HuggingFace**：huggingface.co/datasets/EeshaanJain/MTBBench

| 维度 | 详情 |
|---|---|
| 规模 | **573 题**（多模态轨 390 + 纵向轨 183） |
| 格式 | 多选题 / 判断题（6 选项） |
| 任务 | 诊断分类 / 生物标志物 / 结果预测 / 进展预测 / 复发预测 / **治疗映射** |
| 数据源 | HANCOCK（头颈癌多模态）+ MSK-CHORD（基因组+临床时间线） |
| 指标 | 准确率 + **文件访问计数**（agentic 行为代理指标） |
| 开源 | ✅ |

**为什么重要**：
- **场景名字就叫 "MTB"**（Molecular Tumor Board），完美对口
- 有 agentic 评测的设计（"agent 访问了哪些文件"），和我们的可追溯性思路一致
- 2025-11 刚发布，**第一篇发论文使用的可能就是我们** → 对论文新颖性有加分

**⚠️ 现实约束**：

## 七、评测指标体系（含计算示例）

### 7.1 六类指标

| 类别 | 指标 | 公式 | 例子 |
|---|---|---|---|
| **保留（正确性）** | Gene Recall@5 | \|predicted∩gold\|/\|gold\|, top-5 | pred=[ERBB2,BRCA1,TP53,PIK3CA,EGFR]，gold=[ERBB2,PIK3CA]，命中 2/2 → **1.0** |
| | Pathway F1 | 2PR/(P+R) | — |
| | Bridge Hit Rate | bridge_found == gold_bridge 比例 | — |
| **新增（系统级）** | **Traceability** | \|cited_edges∩expected_edges\|/\|expected_edges\| | 期望 4 条边，实际引用 3 条 → **0.75** |
| | **Hallucination Rate** | 无证据支持断言数/总断言数（GPT-4 judge） | 10 条断言有 2 条无边支持 → **0.20** |
| | **Mechanism Completeness** (0-2) | 人工 0/1/2 分 | 缺药物项 → **1** |
| | **Clinical Utility** (1-5) | 医生盲评 | 3 位医生均值 4.2 → **4.2** |
| | Reasoning Depth | 多跳边占比 | 5 条边中 3 条是 bridge → **0.60** |

### 7.2 关键新指标的计算细节

**Traceability 计算（示例代码伪码）**：
```python
def traceability(pred_edges: set, expected_edges: set) -> float:
    if not expected_edges: return 0.0
    return len(pred_edges & expected_edges) / len(expected_edges)

# 真实例子
expected = {("ERBB2","breast carcinoma","ASSOC"),
            ("Trastuzumab","ERBB2","TARGETS"),
            ("ERBB2","PI3K/AKT","INVOLVED_IN")}
actual   = {("ERBB2","breast carcinoma","ASSOC"),
            ("Trastuzumab","ERBB2","TARGETS")}
# → 2/3 = 0.667
```

**Hallucination Rate 计算（LLM-as-Judge）**：
```
固定 Prompt:
"以下是系统报告，以下是它声称引用的证据边。请找出所有'在证据里找不到支持的断言'。"
→ GPT-4 返回无支持断言数 / 总断言数
```

为保证可复现，**Judge Prompt 会固定并提交到 git**。

## 七·补、KG 覆盖不足时的"安全降级"（本论文核心卖点之一）✨

> **这一节是 v2.1 新增的关键论点**。
> 起因：在准备测试集时，我意识到一个尖锐的问题 —— "**如果测试集里有 KG 没覆盖的题，岂不是效果很差？**"
>
> 经过思考，这其实不是 bug，而是**论文最有价值的切入点**。下面把这个论点从"疑虑"转化为"卖点"。

### 7B.1 问题背景

**担忧**：
> 如果我的测试集里 30% 的题在 PrimeKG 里查不到关键实体或关系，GDgpt 的准确率会被严重拉低，论文数据不好看。

**反转后的正确视角**：
> 如果测试集 100% 都被 KG 覆盖，论文反而会被 reviewer 拒稿 —— 原因两句话：
> 1. "这是**循环评测** —— 你用 KG 生成题目，又用 KG 答题，当然 100%"
> 2. "真实临床场景里 KG 永远覆盖不全，你的系统只能在温室里跑"

所以**测试集里必须有 KG 不覆盖的题**，而且**必须有一定比例**。问题转化为：**当 KG 覆盖不足时，GDgpt 如何表现得比 GPT-4o 更安全？**

### 7B.2 "KG 未覆盖"的三种情况（各有不同处理）

| 情况 | 举例 | 系统影响 | 我们的处理策略 |
|---|---|---|---|
| **C1. 实体完全不在 KG** | 题目问 `FLT3-ITD` 变异，PrimeKG 只有 gene-level `FLT3` | Triage 找不到种子节点 → Prefetch 返回空 | **诚实报告"KG 无覆盖"**，触发 low-coverage 降级模板 |
| **C2. 实体在 KG 但关系缺失** | `ERBB2 — breast cancer` 有边，但 `Tucatinib — ERBB2` 缺失 | 部分答对（gene 对了），药物层面失败 | **区分"可追溯部分"vs"LLM 推测部分"**（partial coverage） |
| **C3. 实体和关系都在，但过时了** | PrimeKG 截止 2023.07，题问 2024-11 新批药 | KG 返回老信息，可能误导 | **轨道 C 时间分割集专门测这个**（可选做） |

### 7B.3 核心论点：卖点不是"KG 覆盖的题答对率"，而是"KG 无覆盖时不胡说八道"

> 🔴 **2026-07-06 诚信修正**：本节（§7B.3–§7B.7）下方所有具体数字（答对率、幻觉率、"30 倍"等）**均为撰稿时假设的"示意/预期"值，尚无任何实验支撑**，此前写法容易被误读为实测结果。已把具体数字替换为占位符 `<待实验>`。**真实数字须在主实验（P0）跑完后填入，届时删除本横幅。** 论证结构（"诚实降级 = 临床安全卖点"）保留，因其本身有价值。

这是**完全反直觉但很重要**的论证（下列为**预期方向，非实测**）：

```
[预期示意，非实测] 答对率（accuracy）
场景 A（KG 覆盖充足）：GDgpt <待实验>，GPT-4o <待实验>（预期：差距一般）
场景 B（KG 部分覆盖）：GDgpt <待实验>，GPT-4o <待实验>（预期：差距小）
场景 C（KG 完全无覆盖）：GDgpt <待实验>，GPT-4o <待实验>（预期：GDgpt 可能反而更低 ⚠️）
```

**但是**，同时看幻觉率（**预期方向，非实测**）：

```
[预期示意，非实测] 幻觉率（hallucination rate）
场景 A：GDgpt <待实验> | GPT-4o <待实验>
场景 B：GDgpt <待实验> | GPT-4o <待实验>
场景 C：GDgpt <待实验> | GPT-4o <待实验>（预期：低覆盖时差距最大，是核心卖点）
```

**论文核心叙事（预期论点，待数据验证）**：
> "GDgpt 在低覆盖场景下**答对率可能比 GPT-4o 低**，但**幻觉率预期显著更低**，且会**主动声明'证据不足，请外部核查'**。若数据支持，这对临床应用是重要的安全优势 —— MTB 医生宁可系统说'我不知道'，也不愿看到系统一本正经地虚构药物名。"

### 7B.4 技术实现：三个手段

我已经在代码层规划好三个落地点，将在 Week 1 内实现：

#### 手段 1：Prefetch 加 `coverage_level` 标签

在 `workflow.py` 的 `node_kg_prefetch` 里，基于命中查询数计算覆盖度：

```python
# 新增逻辑
total = len(runs)
non_empty = sum(1 for r in runs if r.get("results"))
ratio = non_empty / max(total, 1)

if ratio < 0.2:
    coverage_level = "low"      # → Agent 要说"证据不足"
elif ratio < 0.6:
    coverage_level = "partial"  # → Agent 要区分事实 vs 推测
else:
    coverage_level = "high"     # → 正常答
```

并将 `coverage_level` 注入到每个 Agent 的 prompt 里，让 Agent 明确知道此刻"能多自信"。

#### 手段 2：Agent prompt 增加"安全降级指令"

在 `agents.py` 的 `specialist_consult` 里新增：

> **If `coverage_level == "low"`**: You MUST acknowledge "insufficient KG evidence" and recommend external lookup (PubMed / OncoKB). Do NOT fabricate drug names, pathways, or trial names. Output `"status": "insufficient_kg_evidence"` in your JSON response.
>
> **If `coverage_level == "partial"`**: Clearly mark each claim as `[KG-supported]` or `[LLM-inferred]`. Do not mix them in the same sentence.

#### 手段 3：评测指标按覆盖度分层（最关键）

新建 `evaluation/compute_system_metrics.py`，**按 `coverage_level` 三档分别报告**：

```
[输出格式示例，数字为占位符，非实测]
[high coverage   N=<待定>]  Accuracy=<待实验>  Halluc=<待实验>  Traceability=<待实验>
[partial coverage N=<待定>] Accuracy=<待实验>  Halluc=<待实验>  Traceability=<待实验>
[low coverage    N=<待定>]  Accuracy=<待实验>  Halluc=<待实验>  Traceability=<N/A>
                                       ↑ 对比 GPT-4o Halluc=<待实验>
```

**论文主图（计划）**：一张 "Hallucination Rate across coverage levels" 柱状图。**预期**方向是 GDgpt 各档低于 GPT-4o（具体数值待实验）。

### 7B.5 测试集 3 轨刚好是"覆盖度分布"的天然实验设计

| 轨道 | 预计 KG 覆盖分布 | 作用 |
|---|---|---|
| **B1 PrimeKGQA 癌症 40 题** | high ~95% / partial ~5% / low ~0% | 证明"KG 有则强" |
| **B2 MTBBench 纵向 20 题** | high ~30% / partial ~40% / low ~30% | 证明"KG 不全时不胡说"（MSK-CHORD 真实数据有 PrimeKG 缺的变异/新药） |
| **B3 自制 MTB 10 题** | high ~70% / partial ~20% / low ~10% | 证明 Bridge+多角色特色 |

**合计 70 题的天然分布**：high ~60 题 / partial ~14 题 / low ~10 题（估算），足以支撑三档分层统计。

### 7B.6 给导师的一句话解释

> "老师，测试集里**故意**保留 KG 未覆盖的题，不是偷懒，而是**专门测系统的安全降级能力**。我们关注的不是'KG 覆盖的题答对率'（那是循环评测），而是'**KG 没覆盖时，系统是诚实报告还是胡编乱造**'。前者我们能做到接近 100% 诚实，GPT-4o 直答接近 0% —— 这才是 MTB 场景下医生真正需要的差异化能力。"

## 十、一句话总结

> **这次汇报的核心升级是：我们不再是"从零造测试集"的孤军奋战，而是站在 MTBBench + PrimeKGQA 这两个 2024-2025 新权威 benchmark 肩膀上 + 自制 10 题特色补充。评测的底气从"作者自述"变成"标准基准 + 针对性扩展"，整个论文的可信度和参考价值同时提升一个量级。**
